# 同帧粗选、高清保存与流式 OCR

2026-10-16。仅替换抽帧与传递方式，不修改导图生成规则或人物/区域选择策略。

## 流程
顺序解码原始视频帧 → 按现有2/3/4秒间隔取样 → 缩小图用于粗选 → 保留同一帧高清原图 → 原子保存JPEG → OCR → 已有增量同页分组。

高清图不再按粗选时间另行快速跳转提取。选图与保存由两个线程衔接，OCR消费已保存的帧，无须等待全片扫描结束。原始图不涂黑；分析区域、忽略区域和人物轮廓只参与既有比较/识别策略。

两个队列各最多2张，队列满时生产端等待；另保留比较所需的前帧/待确认帧。不会缓存整段视频高清图。取消、换运行身份、解码/保存/OCR失败会终止流水线并释放队列。OCR完成后再次检查取消状态，避免发布过期结果。

## 时间与补采
所有图使用实际PTS相对媒体起点的整数毫秒。首次采样选到点后第一帧，因此实际时间可能比2秒整数网格稍晚。补采选请求时刻正在显示的帧，实际PTS可能稍早；分别传递requestedTimeMs和frameTimeMs，前者校验请求完整性，后者作为真实图像身份、文件名、OCR缓存和时间引用。同一实际帧只入库一次。

补采向前预留解码区间，不能直接信任容器跳转结果；若首帧越过目标，扩大预留直至从头解码。处理非零起点、可变帧率、长GOP及90/180度显示旋转。缺少/回退时间戳、越界、非直角旋转明确报错，不伪造时间。

此前用户视频扩展名为mp4、实际为MPEG-TS。旧快速输入跳转102/104/106秒均可能落到约110秒。新实测分别取得101981/103981/105981毫秒，与从头连续解码画面逐像素相同。该现象并非所有TS视频必然发生。

## 缓存、日志、部署
framePipeline=same-frame-pts-v1加入视觉与下游阶段缓存身份，语音转写缓存不变。不会自动重跑历史任务；下次显式分析不复用旧错误截图的视觉缓存。记录阶段耗时、队列峰值、截图数量、补采请求/实际时间及失败类型，不记录原图、课程正文或模型密钥。使用既有安全轮转日志。

依赖av>=18,<19，当前底包18.1.0。正式Docker构建包含frame_stream.py；覆盖部署也带agent_review.py，并先检查PyAV版本及旋转接口。部署前必须确认无在途任务。

## 2026-10-16 性能回退修复：以本节为当前实现

用户最新30MIN任务dc34cb93-f9d0-4d20-8624-5db7045dcd3e未启用YOLO，visualOcr245.654秒，转写67.465秒，整课261.736秒；历史相同课程visualOcr约93～97秒。确认为v1的逐帧FrameRunGuard磁盘读取开销：30fps视频逐帧检查cancel.json和active-run.json，在Docker/Windows绑定目录上造成数万次I/O。不是每2秒取一张就只解码一张，也不是YOLO引起。

当前流程改为：FFmpeg内部连续解码 → select按原媒体起点的2/3/4秒网格取原始帧 → rawvideo bgr24/NUT管道传出高清原帧及真实PTS → Python缩成320×180做原有粗选 → 有界保存/流式OCR/同页分组。Python不再逐帧接收未采样帧。使用copyts、passthrough和1微秒编码时间基，防止VFR输出被名义帧率量化；无fps滤镜伪造时间。保留sample_frames_pyav仅作离线参考。原有高清补采仍走准确定位方法，解码时也用限频检查。

FrameRunGuard.poll最多每200ms查一次磁盘，线程共享锁及上次检查时间；内存停止信号仍即时检查。在原子保存及OCR结果发布前强制查磁盘，不能以缓存跳过取消/运行身份验证。FFmpeg管道读取时有watcher检查取消并终止child，stderr持续排空避免死锁。提前关闭、取消、错误均回收子进程和线程。仅以最多4096字节临时缓冲分类stderr，不保存原始错误正文；记录退出码及安全分类。缓存身份sampled-ffmpeg-pts-v2，仅视觉及下游失效，不影响转写缓存、不自动重跑历史。
