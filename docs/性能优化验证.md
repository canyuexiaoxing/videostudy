# 分析性能优化验证（2026-10-02）

## 已部署配置

- 补采检查：每 10 分钟一个窗口，前后各 30 秒上下文，最多 3 个 API 请求同时运行。
- 不同窗口的同轮检查汇总后，检查时间归属、按已有证据规则去重，统一批量补采。第二轮只检查提出了有效补采请求的窗口，并带上补采后的 OCR；仍最多两轮。
- 页面理解：最多 5 页同时处理；同一页内部的遮挡补图、计算核验仍依次执行。最终按原页面顺序汇总。
- 转写与画面粗选/OCR 同时运行。
- 补采截图：一次 FFmpeg 进程最多输出 8 张，逐个时间点快速定位。不扫描两个相隔很远的时间点之间全部画面。8 是批大小，不是全视频补采上限。
- OCR：独立进程跨视频任务保留模型，一次服务一个视频的视觉任务；每次使用前重新绑定文件与输出目录。服务退出时清理进程。

这些优化未加入全视频截图总量上限，也未恢复模型输出 Token 上限。

## 真实样本计时

使用项目中的 `30MIN.mp4` 和现有 Whisper、PP-OCRv6、DeepSeek 配置。每个设置仅测量一次，结果受硬件、缓存和 API 响应波动影响。

| 测量步骤 | 对照 | 优化后 | 验证范围 |
|---|---:|---:|---|
| 5 张补采截图 | 逐张启动 FFmpeg：1.223 秒 | 批量提取：0.306 秒 | 同一组 5 个时间点 |
| 单张截图 OCR | 新进程首次识别：7.785 秒 | 复用模型进程：4.065 秒 | 包含模型初始化与截图、识别；不能解释为纯 OCR 运算减半 |
| 60 秒真实课程转写与视觉 OCR | 串行：15.943 秒 | 并行：12.817 秒 | 两次均 34 段转写、3 张画面；未逐字证明结果完全相同 |
| 5 页真实课程图片理解 | 1 并发：47.210 秒 | 5 并发：11.305 秒 | 两次均按 1～5 页返回；全部为 `unverified`，没有 `failed` |

`unverified` 表示模型有无法确认的内容，保留已确认部分与具体问号，并非课程内容已全部理解正确。此处只验证响应可用、顺序正确与耗时，不能据此断言学习内容质量达标。

补采检查 1 并发测得 14.416 秒、补采 2 张；3 并发测得 0.694 秒、补采 0 张。由于两次模型判断不同，执行步骤不同，这两个总耗时不能作为公平的并发加速比。分段调度的并发与去重另由受控回归测试验证。

未重新跑完整 30 分钟课程的全部分析，因此不能给出整段视频最终总耗时。Python 结果新增 `stageTimingsMs`，记录各阶段与总时长；并行步骤的耗时不能相加，前端暂未展示。

## 测试中发现并修复的问题

真实页面请求原来有时漏掉必填 `corrections`，或把字符串列表返回成对象列表。串行与并行均可出现。已明确必填字段及类型，并在有限的格式重试中附加缺失字段和返回结构的修复反馈。没有放松证据、算式或不确定性校验规则。

完整 Python 回归测试共 66 项通过，开启 `RUN_MEDIA_INTEGRATION=1`，包含实际 FFmpeg、Whisper、OCR 媒体链路；集成测试里的模型返回是受控替身，真实 API 页面计时另行执行。模型负面用例主动打印的失败提示属于预期测试，不是未通过用例。

## 资源与部署

媒体并行的 CPU、内存峰值更高，OCR 常驻会持续占内存。API 并发主要增加同时请求数与图片编码内存，同样调用量的费用大致不变，重试会增加调用。测试中一次容器采样约 1.6 GiB、CPU 约 1006%（多核合计），它不是完整运行的峰值统计。

`.env` 的 `REVIEW_CONCURRENCY`、`PAGE_CONCURRENCY` 可调并发，`MEDIA_PARALLEL=0` 可关闭媒体并行。当前服务实际生效值为 `3`、`5`、`1`，健康检查通过。

本地发布复用了已经验证的依赖镜像，更新分析源码。没有重新验证从零下载依赖的标准构建，也没有改动用户的模型或密钥。

详细测量输出保存在忽略目录 `.local/qa/performance-benchmark.json` 与 `.local/qa/performance-pages-repaired.json`，没有写入用户课程历史。

## 第二次优化：粗选批量提图与精简重复请求

粗选后的正式截图已改为复用批量 FFmpeg 提取。选图算法、选中的时间点、图像分辨率和保存位置保持原有约定，每批最多 8 张，不限制总张数。对这份真实课程已有的 74 个粗选时间点单次测量：逐张提图 20.753 秒，批量提图 6.780 秒；两次均输出 74 张 1920×1080 图片。该测量仅包含提图，不包含粗选扫描、OCR 或整节课导图生成。

页面请求本来就按对应语音时间窗发送，本次没有进一步删减语音。只在发送 API 时把重复字段编码成列名与数据行表格；补采检查中的相同 OCR 字符串共享一份字典，各帧用索引引用，保留每次出现、顺序和时间。内部处理、数据库结果和前端结构不变。格式重试只保留最近一次无效响应及修复反馈，不再逐轮累积旧响应；每次请求仍包含原始证据，因为 HTTP API 不会自动记住上一请求。

真实样本中的证据 JSON 字符数（两种格式都去除非必要空格）变化：

| 材料 | 原字符数 | 精简后 | 减少 |
|---|---:|---:|---:|
| 第一段补采检查 | 15,114 | 8,791 | 41.8% |
| 第一页语音＋OCR | 2,834 | 1,628 | 42.6% |
| 第一页图片路线的语音上下文 | 1,450 | 952 | 34.3% |

这只是证据 JSON 的字符数，不是整个请求大小或计费 Token 数。提示词、图片 Base64 与输出没有计入；图片没有压缩或减少。本次没有测量完整课程总耗时变化。

精简格式的两条页面路线均经真实 API 调用，返回 `unverified` 的可用结构（存在无法确认的内容，未断言全部正确）。补采模型的小样本检查：未念出的表格数值提出 9000 ms 补采，仅提到线条时不补采。它验证模型能使用编码，不代表漏检率已达标。

完整 Python 测试现为 71 项通过，包含真实媒体集成。服务已部署 `page-evidence-v5`、`visual-review-v6`。相关输出见 `.local/qa/coarse-extraction-benchmark.json` 与 `.local/qa/compact-request-validation.json`。
